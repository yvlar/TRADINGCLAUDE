### Sprint 175 — E4-S10 : provisionnement de clés API par tenant ✅

**Objectif :** Rendre le rattachement tenant des clés API (S168) **pilotable côté produit** — un admin provisionne une clé pour un tenant choisi via un champ `tenant_id` optionnel sur `CreateKeyRequest`, au lieu d'hériter silencieusement du tenant courant. Prérequis d'un onboarding multi-tenant. Sprint backend léger (endpoint admin + garde service), sans migration ni frontend.

**Décision tranchée — autorisation fail-closed (option a) + correctif JWT (revue)** : la carte laissait le choix entre (a) restreindre au tenant courant et (b) introduire un super-admin. Retenu **(a)**, minimal et fail-closed : un admin ne peut viser que **son tenant courant** (`get_current_tenant()`), sinon **403** — pas d'escalade cross-tenant. **Seule la clé env / super-admin legacy** en est exemptée (onboarding multi-tenant). **Correctif issu de la revue indépendante** : `_admin is None` ne suffit PAS comme signal d'exemption — le chemin **cookie JWT** pose lui aussi `api_key_record=None` (`app/middleware/auth.py:174`), si bien que tout utilisateur web (même `reader`) était traité en super-admin. La distinction repose désormais sur `request.state.user_id` (posé uniquement par le chemin JWT, dérivé du JWT signé) : `_require_admin` **exige le rôle admin pour un utilisateur JWT** (sinon 403, fermant un fail-open pré-existant sur les 4 endpoints admin), et l'exemption cross-tenant est **strictement la clé env** (`_admin is None and not _is_jwt_user(request)`). Ordre des contrôles **403 avant 404** (un admin non autorisé ne sonde pas l'existence d'un tenant tiers).

**Livrables :**
- `app/api/endpoints/admin.py` — `CreateKeyRequest.tenant_id: UUID | None = None` (absent → tenant courant, rétrocompatible) ; helper `_is_jwt_user(request)` (présence de `user_id`) ; `_require_admin` exige le rôle admin pour un utilisateur JWT (la clé env sans `user_id` reste admin implicite) ; `create_key` applique la garde cross-tenant (403, exemption clé env uniquement), vérifie l'existence du tenant cible **avant** l'INSERT (`service.tenant_exists` → **404**, jamais une violation FK 500), thread `tenant_id=body.tenant_id` à `service.create_key` (résolu par `resolve_tenant` : `None` → courant, valeur → ce tenant) et journalise le `tenant_id` effectif.

### Sprint 174 — E4-S9 : facturation à l'usage métrée vers Stripe ✅

**Objectif :** Fermer la boucle de monétisation — pousser la consommation agrégée (`usage_events`) vers Stripe en **metered usage records**, pour facturer l'usage réel *en plus* de l'abonnement forfaitaire (partie « facturation à l'usage » différée au S172). 9ᵉ marche de l'épic E4 ; sprint backend (worker + service Stripe + migration).

**Décision tranchée — API du SDK (anti-hallucination)** : la carte citait `SubscriptionItem.create_usage_record` comme API possible « selon la version ≥15 ». Vérification du SDK **réellement installé (`stripe 15.2.0`)** : les *usage records* historiques sont **retirés** ; seule la **Billing Meters API** (`stripe.billing.MeterEvent.create`) existe. Choix retenu (la carte déléguait : « ne pas supposer », « signature équivalente ») : le metered record cible un **customer** (`stripe_customer_id` persisté) + un **nom d'événement de meter**, pas un `subscription_item`. La clé `.env` est donc `STRIPE_METER_EVENT_NAME` (et non `STRIPE_PRICE_METERED` — un price id serait du config mort pour le report).

**Livrables :**
- `app/services/stripe_service.py` — `report_usage(customer_id, quantity, *, timestamp, identifier=None)` : metered record via `stripe.billing.MeterEvent.create` déporté en `asyncio.to_thread` (clé par appel `api_key=`, jamais loggée ; `payload={"stripe_customer_id":…, "value": str(quantity)}`). **No-op loggé** si `is_metered_configured` faux (clé secrète + `STRIPE_METER_EVENT_NAME`) — distinct de `is_configured` (abonnement/webhook). `meter_event_name` ajouté au constructeur (défaut `None`, threadé au lifespan `main.py`).
- `app/services/usage_event_service.py` — `count_events_in_window(since, until)` **lecture seule** (contrat append-only étendu `{record, aggregate, count_events_in_window}`) : `COUNT(*)` des `usage_events` sur `(since, until]` (borne basse exclue / haute incluse → fenêtres consécutives sans chevauchement ni trou) ; `since=None` → tout l'historique. **Aucun `WHERE tenant_id`** : isolation par la RLS (l'appelant pose `tenant_scope`). - `app/workers/tasks.py` + `celery_app.py` — `run_usage_reporting` (clonée sur `run_retention_purge`) : pour chaque abonnement `active` avec `stripe_subscription_id`+`stripe_customer_id`, agrège `count_events_in_window((curseur, now])` **sous `tenant_scope`**, pousse le metered record, puis avance le curseur → `now()`. **Best-effort par tenant** (un échec n'avorte pas les autres et **n'avance pas son curseur**). `beat_schedule` **quotidien 02h00 UTC** (avant la purge 03h00). No-op si meter non configuré (aucune itération). Aucune clé loggée.

Garde contre le « report OK, commit du curseur KO » : l'`identifier` Stripe est keyé sur la **borne basse** de la fenêtre (`since`), stable tant que le curseur n'a pas avancé → un re-rejeu de la même fenêtre porte le même identifiant → **Stripe le dédupe** (facturation *at-most-once*).

**Preuve d'acceptation observable** : worker exécuté avec `count_events_in_window` + SDK Stripe mockés → un tenant abonné consommant N unités produit **un** metered record de quantité N ; une 2ᵉ exécution sur la même fenêtre (curseur posé) **ne re-rapporte pas** (tests `test_deux_runs_consecutifs…` bout-en-bout via curseur mutable + `test_identifier_stable…` prouvant la déduplication). **Pas de validation Stripe réelle** (SDK mocké — pas de Docker/clé dans le conteneur web).

**Version** : 10.61.0
**Tests** : 2 268 backend collectés (2 237 passés, 30 skipped, 1 xfailed — **+32** : forme migration `0010` [chaînage, colonne nullable, hors RLS, downgrade] ; unitaires `StripeService` [`is_metered_configured` vrai/faux/indépendant du webhook, `report_usage` transmet customer/quantity/timestamp/identifier, clé par appel, no-op si non configuré, aucune clé loggée] ; unitaires `count_events_in_window` [fenêtre bornée `(since, until]`, `since=None` → tout, jeu vide → 0, aucun `WHERE tenant_id`] ; worker `run_usage_reporting` [report 1ᵉʳ run quantité N, COUNT sous `tenant_scope`, idempotence 2 runs + identifier stable, no-op non configuré, best-effort un échec n'interrompt pas les autres + n'avance pas le curseur, `beat_schedule` 8→9]) ; `ruff`/`mypy app/` (166 fichiers) verts ; **frontend non touché** ; **pas d'eval** (aucun prompt de skill ni l'orchestrateur de skills touché — service Stripe + worker + migration uniquement).
