### Sprint 178 — E4-S12 : retour de checkout Stripe sur la page Facturation (UX) ✅

**Objectif :** Après un retour de checkout Stripe (`/facturation?status=success|cancel`, déposé par `billing.py:81-82`), `BillingPage` ne faisait rien : ni confirmation, ni rafraîchissement du plan affiché. Comme le webhook met `tenants.plan` à jour **de façon asynchrone** alors que `user.plan` du contexte est figé au montage (`authMe()` une seule fois), un tenant venant de passer à `pro` voyait encore le CTA « Passer à Pro » jusqu'à un rechargement complet (friction produit immédiate). Sprint **frontend** (page Facturation + contexte d'auth), aucune migration ni endpoint backend.

### Sprint 175 — E4-S10 : provisionnement de clés API par tenant ✅

**Objectif :** Rendre le rattachement tenant des clés API (S168) **pilotable côté produit** — un admin provisionne une clé pour un tenant choisi via un champ `tenant_id` optionnel sur `CreateKeyRequest`, au lieu d'hériter silencieusement du tenant courant. Ordre des contrôles **403 avant 404** (un admin non autorisé ne sonde pas l'existence d'un tenant tiers).

**Livrables :**
- `app/api/endpoints/admin.py` — `CreateKeyRequest.tenant_id: UUID | None = None` (absent → tenant courant, rétrocompatible) ; helper `_is_jwt_user(request)` (présence de `user_id`) ; `_require_admin` exige le rôle admin pour un utilisateur JWT (la clé env sans `user_id` reste admin implicite) ; `create_key` applique la garde cross-tenant (403, exemption clé env uniquement), vérifie l'existence du tenant cible **avant** l'INSERT (`service.tenant_exists` → **404**, jamais une violation FK 500), thread `tenant_id=body.tenant_id` à `service.create_key` (résolu par `resolve_tenant` : `None` → courant, valeur → ce tenant) et journalise le `tenant_id` effectif.

**Preuve d'acceptation observable** : matrice d'intégration `POST /admin/keys` sur 4 personas — sans `tenant_id` → `create_key` reçoit `None` (inchangé, `tenant_exists` non appelé) ; `tenant_id` = tenant courant (admin DB **ou** admin JWT) → **201**, `ApiKeyRecord.tenant_id` correct ; `tenant_id` ≠ courant (admin DB **ou** admin JWT) → **403**, aucune création ; **JWT reader → 403** (`_require_admin`) ; **clé env** + tenant arbitraire → **201** (seule exemption) ; `tenant_id` inexistant → **404**, aucune création.
